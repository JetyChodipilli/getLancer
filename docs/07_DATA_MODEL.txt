DATA MODEL
1. Modeling Principles
PostgreSQL is the source of truth.
Use relational constraints for core marketplace relationships.
Use JSONB only for non-core flexible metadata.
Preserve historical inquiry/outcome references even if products are archived.
Avoid hard-coding product ownership in a way that prevents future team ownership/contributors.
Use soft delete where auditability matters.

5. Validation Rules
User
Valid normalized email
Strong password policy
Unique slug where applicable
Product
Title: reasonable min/max length
Summary: short
Description: capped
Contribution required
At least one category
Technology optional only when not meaningful
Activation requires approved developer + approved product + free slot
Public live URL must pass safe URL validation
Inquiry
Valid email
Description required
Budget controlled enum
Timeline controlled enum
Reference product must exist
Target developer must match product owner/eligible recipient
Rate limits per email/IP/account
Review
Rating 1–5
Confirmed completed inquiry required
One verified review per engagement

Search:

pg_trgm index on title/summary where useful
8. Soft Delete
Soft delete recommended for:
users
products
reviews where legal/moderation retention applies
Hard delete/retention policy must comply with user deletion/privacy obligations.
Public content must disappear immediately after user-authorized deletion even if internal retention continues temporarily for legal/security reasons.
9. Auditability
Never overwrite important marketplace history.
Preserve:
Inquiry event history
Approval decisions
Moderation actions
Hire confirmation
Completion confirmation
Review eligibility

11. Backup Strategy
Daily automated DB backups minimum
PITR when supported
Object-storage durability/versioning
Encrypted backups
Separate backup credentials
Document restore
Test restore
12. Data Recovery Priorities
Highest priority:
Users
Products
Inquiries
Inquiry history
Reviews
Moderation/audit
Analytics
Analytics can be rebuilt more easily than marketplace history.
13. Data Migration Rules
Every schema change via migration tool
No manual production schema edits
Migrations tested on staging
Backward compatibility preferred
Destructive migrations require explicit plan
