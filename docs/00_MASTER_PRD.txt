This document defines what must be built now, what must be measured, and what is deliberately postponed.
1. Project Vision
1.1 Purpose
Create a global proof-of-work marketplace where developers showcase real software products and client case studies, clients discover builders through working evidence rather than resumes alone, and qualified client inquiries are routed to the relevant developer. V1 is a lead-generation and proof-of-work discovery platform; contracts and payments remain external.
1.2 Problem Statement
Freelance marketplaces often begin with profiles, proposals, or bidding instead of showing what a developer has actually built.
Developer portfolio sites provide proof but usually do not create a structured client-intent and lead pipeline.
Clients struggle to judge technical capability, relevance, availability, responsiveness, and whether a builder has solved a similar problem.
Developers struggle to convert portfolio traffic into qualified project opportunities.
Early marketplaces can be damaged by low-quality project spam, fake work, inactive developers, and unqualified client inquiries.
1.3 Target Audience
User Segment | Initial Need
Individual developers / freelancers | Showcase strong products, receive qualified client leads, build reputation.
Experienced engineers | Show commercial/client work, including private or NDA-safe case studies.
Students / early-career builders | Show genuine products and build proof-of-work, subject to quality approval.
Startups and founders | Find builders who have already built similar software.
SMEs and local/global businesses | Discover relevant applications and request custom builds.
Agencies / studios | Later: recruit proven developers and accept larger client projects.
1.4 Product Principles
Proof before pitch: product evidence is primary; profile claims are secondary.
Client friction must stay low: basic browsing and inquiry submission remain simple.
Trust is earned, not sold.
Quality beats raw registration count.
No public bidding war in V1.
External contracts/payments are acceptable in V1; the platform still tracks the lead and outcome.
Global product, curated launch.
1.5 Success Criteria for V1
Metric | Initial Validation Target
Curated developers | 20 approved builders
Quality active showcases | 50–60 total
Showcases with usable proof | Majority include live deployment, demo video, or credible client case study
Qualified client inquiries | 5–10 initial qualified inquiries
Serious client-builder discussions | 2–5
Paid engagements originating from platform | 1–3
Developer response tracking | Enabled for every inquiry
Outcome tracking | Hired / Not Hired / Completed captured
1.6 North-Star Metric
V1 north-star metric: Qualified Client–Builder Connections per Week.
Later progression: Successful Client–Builder Hires per Month → Completed Marketplace GMV.

Existing earned and purchased allowances remain valid.

2.6 Product Approval Workflow
Developer submits → Pending Review → Admin reviews → Approve / Request Changes / Reject.
Check demo relevance and quality.
Check external URL reachability and obvious risk.
Check description/category/technology consistency.
Check for obvious copying, impersonation, stolen screenshots, or misleading claims.
Check developer contribution statement where multiple people were involved.
Trusted-builder auto-publishing is deferred until sufficient reputation and moderation data exist.
2.7 Search and Discovery
Search by product title, problem/business category, technology, and builder.
Business-problem categories appear before technology-only categories in client discovery.
Filters: category, project type, availability, live-demo availability, technology.
Basic sorting: relevance, newest, recently updated.
Popularity/upvotes must not be the sole ranking mechanism.
Search results must expose product proof and builder availability without requiring profile-first navigation.

2.9 Inquiry Status and Outcome Tracking
Status | Meaning
Inquiry Received | Lead stored and developer notified.
Responded | Developer responded to client.
Discussion | Requirements are being discussed.
Proposal Sent | Developer/team has sent commercial proposal externally or by email.
Hired | Client selected developer; should be client-confirmed.
In Progress | Work has started.
Completed | Work completed; should be client-confirmed.
Not Hired | Opportunity closed without hire.
Important outcomes such as Hired and Completed should support dual confirmation by client.
Outcome events must be auditable with timestamps.
V1 tracks reported project value optionally; it does not process payment.
2.10 Reviews
Only verified completed client relationships can create a marketplace review.
One verified review per completed engagement unless support/maintenance is intentionally treated as a separate engagement.
Store rating, text feedback, completion date, associated product/inquiry, and moderation status.
Admins can hide/remove abusive, fraudulent, or policy-violating reviews.
Open unverified testimonials must not be mixed with verified marketplace reviews.
2.11 Availability and Reliability
Developer availability states: Available Now, 1 Slot Left, Limited Availability, Booked Until [date], Not Taking Work.
Track inquiry response rate and median/typical response time.
Repeatedly ignored qualified inquiries may reduce discovery priority.
If selected developer is unavailable, V1.5 should recommend similar available builders.
2.12 Notifications
Email: account verification, inquiry received, inquiry status confirmation, admin review result, review request.
In-app notification center for essential events.
No full real-time chat required in V1.
Notification preferences should be introduced as volume grows.
2.13 Error Handling
Custom 404 page.
Custom 500 / unexpected error page.
Friendly validation errors on forms.
Graceful handling for failed external demo URLs.
Rate-limit / abuse messages should be explicit.
Offline fallback for public browsing is optional; a full offline application is not required in V1.
2.14 Admin and Moderation
Review pending developers and products.
Approve, reject, or request changes.
View reports and moderation history.
Suspend users or unpublish products.
Manage business categories and technology tags.
Inspect inquiry abuse patterns.
Audit critical moderation actions.
2.15 Core User Stories
Actor | User Story
Developer | As a developer, I want to publish my strongest working products so that clients can judge my capability from evidence.
Developer | As a developer, I want to receive qualified inquiries tied to a specific product so that I know why the client contacted me.
Developer | As a developer, I want to archive a showcase and reuse the slot so that I can keep my active portfolio current.
Client | As a client, I want to search by what I need to build so that I can find relevant working examples.
Client | As a client, I want to watch a demo and open a live application before contacting a builder.
Client | As a client, I want to request something similar without creating a complicated account first.
Admin | As an admin, I need to approve projects and remove misleading or unsafe listings to protect marketplace trust.
Platform | As the platform, I need to know which product generated an inquiry and whether that inquiry resulted in a hire.
3. Non-Functional Requirements
3.1 Performance
Area | Target
Public page load | Core content should become usable quickly on standard broadband/mobile connections; optimize media loading.
Common read API p95 | Target <= 400 ms under expected V1 load; simple cached/read endpoints should aim lower.
Search response | Target <= 1 second for V1 data volume.
Inquiry submission | User receives confirmation immediately after durable persistence; notification delivery may be asynchronous.
Image delivery | Responsive sizes, lazy loading, compression, CDN/object-storage delivery.
3.2 Scalability
V1 architecture should comfortably support the initial validation cohort without distributed-system complexity.
Stateless application instances should allow horizontal scaling later.
Database access must use indexing and pagination for search/listing endpoints.
Media must not be stored in the application container filesystem.
Design for growth to tens of thousands of accounts before considering service extraction; exact scaling decisions must follow observed load.
3.3 Availability and Resilience
Production application target availability should be appropriate for an early-stage SaaS marketplace.
Use managed or automated database backups.
Graceful degradation when third-party email, analytics, or demo URLs fail.
No single user-submitted external demo should be able to affect platform availability.
3.4 Security
TLS/HTTPS for all production traffic.
Secure password hashing if password auth is used.
JWT/session tokens must be signed, expiring, and handled securely; prefer HttpOnly secure cookies for browser sessions where suitable.
OAuth tokens stored only when needed and encrypted/protected.
Role-based authorization for admin and future team roles.
Rate limiting for authentication, inquiry submission, and reporting endpoints.
Input validation and output encoding.
CSRF protection where cookie-based authentication is used.
File upload restrictions: MIME/type checks, size limits, safe naming, malware scanning where feasible.
SSRF protections when validating developer-submitted URLs; block localhost, private IP ranges, metadata endpoints, and unsafe schemes.
Secrets must be stored in environment/secret-management systems, never in source control.
Audit admin actions and sensitive status changes.
3.5 Privacy and Compliance
GDPR-ready consent, data access, correction, and deletion workflows for global users.
CCPA/CPRA applicability to be reviewed based on business scope and thresholds.
Collect only data needed for marketplace operation.
Define retention rules for inquiries, deleted profiles, logs, and moderation evidence.
Cookie consent/configuration where non-essential tracking cookies are used.
Accessibility target: WCAG 2.2 AA for public and core authenticated experiences.
3.6 Accessibility
Keyboard-accessible navigation and forms.
Visible focus states.
Semantic headings and landmarks.
Form labels and error associations.
Sufficient contrast.
Alt text for meaningful uploaded images where required.
Captions/transcripts encouraged for demo videos.
No critical flow should depend only on color.
4. System Architecture
4.1 V1 Architecture Decision
Use a modular monolith for V1. Do not introduce Kafka, gRPC, Kubernetes, or a microservice fleet before real scale or team boundaries justify them.
4.2 Recommended Tech Stack
Layer | Recommendation
Frontend | Next.js / React + TypeScript
Backend | Spring Boot
Architecture | Modular monolith
Database | PostgreSQL
Persistence | Spring Data JPA / Hibernate with explicit query tuning where needed
Auth | Spring Security + OAuth2; secure browser session or JWT strategy
Object storage | S3-compatible storage for images/thumbnails
Demo video | External YouTube/Loom links in V1; no self-hosted video pipeline
Search | PostgreSQL full-text/trigram search initially
Email | Transactional email provider
Analytics | Product analytics platform or first-party event tracking
Error monitoring | Centralized application error tracking
Deployment | Dockerized frontend/backend; managed VM/PaaS/container service
CI/CD | GitHub Actions or equivalent
4.3 Backend Module Boundaries
Module | Responsibility
auth | Authentication, verification, password reset, OAuth.
users | Base account state and role assignments.
profiles | Developer/client profile data.
products | Showcases, media metadata, categories, visibility, slots.
search | Product/builder discovery and filters.
inquiries | Client requirements, budget/timeline, status workflow.
reviews | Verified post-completion reviews.
notifications | Email and in-app notifications.
moderation | Reports, approvals, suspensions, audit records.
analytics | Conversion events and marketplace funnel metrics.
admin | Administrative workflows and controlled settings.
4.4 Deferred Architecture
Kafka: defer until asynchronous workloads and throughput justify operational complexity.
gRPC: defer until independently deployed services need high-performance internal RPC.
Microservices: defer until organizational/service boundaries are proven.
Kubernetes: defer until deployment scale and operational needs justify it.
Dedicated search engine: defer until PostgreSQL search no longer satisfies relevance/performance requirements.
Real-time WebSocket messaging: defer until in-platform messaging becomes a validated requirement.
4.5 Integration Points
Email provider for verification and inquiry notifications.
GitHub OAuth and optional repository/profile links.
S3-compatible storage/CDN for images.
External video hosts such as YouTube/Loom.
External demo URLs hosted by developers.
Analytics/error-monitoring services.
Payments provider is explicitly deferred.

6.2 Data Validation Rules
Normalize and validate email addresses.
Enforce reasonable text-length limits on titles, summaries, descriptions, and inquiry fields.
Reject unsupported URL schemes.
Block localhost, loopback, link-local, private network ranges, and cloud metadata targets in demo URL checks.
Validate file type and file size before upload.
Use server-side validation even when client-side validation exists.
Sanitize or safely render user-generated rich text; prefer restricted Markdown/plain text initially.
Budget and timeline values must use controlled enums/bands in V1.
Product cannot become active until approved.
Active showcase count cannot exceed the builder's entitlement.
6.3 Data Integrity
Every inquiry must preserve its originating product and target developer at submission time.
Status history must be append-only/auditable even if current status changes.
Review must reference a confirmed completed inquiry/project relationship.
Deleted/archived products must not silently erase historical inquiry/review references.
Use soft deletion where auditability is required.
6.4 Backup and Recovery
Automated daily database backups at minimum; higher frequency as traffic/value grows.
Object-storage versioning or equivalent recovery where practical.
Document and test database restore procedure.
Define retention and purge policy.
Production credentials and backup encryption keys must be protected separately.

7.5 Logging
Structured logs with request/correlation IDs.
Never log passwords, raw auth tokens, or sensitive secrets.

7.6 Developer Demo Deployment Model
V1 does not host developer applications. Developers deploy externally and provide a public or private demo reference.
Reject localhost/private-network URLs for public demos.
Store and validate live URL.
Periodically check reachability in V1.5.
Never execute arbitrary developer code on the production application servers.
Platform-hosted demos are deferred to a future paid/isolated service.

14. Final V1 Scope Statement
V1 is successful if it proves that a client can discover a real software showcase, understand the builder's contribution, submit a qualified request, reach the developer, and generate a real paid development engagement.
Everything else—teams, payments, source-code sales, hosted demos, AI matching, microservices, and advanced marketplace infrastructure—must remain secondary until this core loop is repeatedly validated.
