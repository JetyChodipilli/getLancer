ARCHITECTURE
1. Architecture Decision
V1 Recommendation
Use a modular monolith:
Next.js/React frontend
Spring Boot backend
PostgreSQL
S3-compatible object storage
External demo/video hosting
Transactional email provider
Docker deployment
GitHub Actions CI/CD
Do not start with microservices, Kafka, gRPC, or Kubernetes.
Reason:
The primary risk is marketplace validation, not distributed-system scale.

4. Request/Data Flow — Product Publishing
sequenceDiagram
    actor Dev as Developer
    participant Web as Next.js
    participant API as Spring Boot
    participant DB as PostgreSQL
    participant Store as Object Storage
    actor Admin as Admin

    Dev->>Web: Create product draft
    Web->>API: POST /products
    API->>DB: Save draft

    Dev->>Web: Upload screenshots
    Web->>API: Request upload
    API-->>Web: Signed upload details
    Web->>Store: Upload file

    Dev->>Web: Submit for review
    Web->>API: POST /products/{id}/submit
    API->>DB: Validate profile + slot potential + set PENDING_REVIEW

    Admin->>Web: Review queue
    Web->>API: GET pending products
    Admin->>Web: Approve
    Web->>API: POST /admin/products/{id}/approve
    API->>DB: Activate if entitlement allows

9. Authentication / Session Design
For browser-first V1:
Spring Security
OAuth2/OIDC where used
Secure HttpOnly cookie-based session or signed token session
CSRF protection where relevant
Avoid long-lived JWT in browser localStorage
JWT can still be used for carefully designed stateless APIs, but the requirement is secure authentication, not "JWT everywhere."
10. PostgreSQL
Use PostgreSQL for:
Accounts
Profiles
Products
Categories
Tags
Entitlements
Inquiries
Status history
Reviews
Reports
Notifications
Audit events
Analytics facts/aggregates as appropriate
Use:
UUID/ULID or bigint IDs consistently
Foreign keys
Unique constraints
Partial indexes where helpful
JSONB only for flexible metadata, not core relational data
Full-text/trigram search initially
11. Object Storage
Use S3-compatible storage for:
Product screenshots
Thumbnails
Avatars
Later: approved documents
Do not store uploads on application container disk.
Recommended flow:
Frontend
→ API requests signed upload
→ Upload directly to object storage
→ API records metadata

15. Background Jobs
Use a lightweight queue/job system initially.
Jobs:
Email
Demo health checks
Cleanup
Aggregation
Image processing
Options:
Database-backed job table
Spring scheduling for low-scale periodic tasks
Lightweight queue service later
Kafka is not justified for V1.
16. Search Architecture
V1
PostgreSQL:
Full-text search
pg_trgm
Indexed filters
Upgrade Trigger
Consider Typesense/Meilisearch/OpenSearch only if:
Relevance requirements exceed PostgreSQL
Search latency degrades
Faceting becomes complex
Dataset becomes large
Semantic matching is introduced
17. Caching
Do not add Redis by default unless needed.
Add when measured benefit exists for:
Hot public pages
Rate limiting
Session store
Search filter metadata
Expensive aggregates
CDN caching of public assets/pages may provide more value earlier.

19. Environment Separation
Local
Development
Staging
Production
Each must have:
Separate database
Separate secrets
Separate OAuth callbacks
Separate email configuration
Separate object storage namespace/bucket
Never point staging at production DB.
20. Observability
Centralized error tracking
Structured logs
Request IDs
Metrics
Health endpoints
Alerting
Spring Boot Actuator may expose protected health/metrics endpoints.
Never publicly expose sensitive actuator endpoints.
21. Microservices Roadmap
Potential future extraction only after proven need:
identity-service
marketplace-service
search-service
notification-service
payments-service
media-service
verification-service
But extraction is a future operational decision.
Kafka Trigger
Use only when there is a need for:
Large event throughput
Multiple independent event consumers
Replayable event streams
Strong decoupling across services
gRPC Trigger
Use only when:
Multiple internal services exist
Strict typed internal RPC is beneficial
REST overhead actually matters
22. V2 Team Architecture Readiness
V1 schema/API should be extendable for:
organizations
organization_members
organization_roles
team-owned products
product contributors
team inquiries
team recruiting roles
Avoid hard-coding every product to exactly one permanent human owner in a way that cannot evolve.

KYC/KYB
