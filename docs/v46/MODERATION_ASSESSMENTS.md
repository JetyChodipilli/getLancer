# Private component review assessments

Normal component review requires separate originality, quality, licence and execution results, each with a 20–1000 character evidence note. Results are `PASS`, `FAIL` or `NOT_APPLICABLE`; a not-applicable result requires the same evidence note. An approval requires passing originality, quality and licence checks. Runnable source also requires passing execution; only source explicitly classified as `Source only` permits a not-applicable execution result.

The server rechecks current administrator authority, locks the owner capacity and exact submission, and compares the full source/setup/licence/context SHA-256 and revision. It then commits the state change, any immutable source release, and an append-only `component_review_assessments` record in the same transaction. The record binds the actual administrator, reviewed revision, full hash, decision, reason, four assessment objects and timestamp. Failed validation, stale bindings or insufficient authority create no assessment or publication.

Assessment notes are administrator-only. The authenticated administrator detail response includes the latest 20 history records. Public catalogue/detail/source/version responses and builder detail responses do not project the table or its notes. The existing shared review reason remains separate from private criterion evidence. Existing publications receive no fabricated backfilled assessments; a subsequent normal review must supply them.

An appeal restoration is a distinct operation. Existing recovery checks prove that the precise already released source and public context match the original reported artifact, that the suspension generation is still current, and that the owner, capacity and administrator remain eligible. Its private history is labelled `APPEAL_RESTORE`, references the original moderation decision, and contains no fresh assessment objects. HTTP review commands cannot request this internal classification. This preserves recovery without claiming that an appeal silently reran the four publication checks.

Verification includes required/malformed evidence rejection, failing and not-applicable approval rejection, exact hash/revision matching, current role/MFA checks, private projections, append-only database protection, explicit failed evidence for change requests and suspensions, appeal provenance, and browser input retention/retry/current-authority denial. Browser checks are automated; they do not establish human accessibility acceptance or legal licence approval.
