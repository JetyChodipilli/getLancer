## Why the repairs kept exposing another failure

The workflow has sequential, fail-fast stages. Frontend dependency checks precede lint and TypeScript, which precede native material verification, the complete Node suite and focused/browser suites. A stage that never ran could contain a latent defect. Consequently, clearing lint exposed type errors; clearing types exposed generated material drift; clearing source/extraction tests allowed browser request and accessible-label failures to become visible. Passing one stage was insufficient evidence for later stages. Independent backend and lab jobs also exposed different defects in the same run.

Several repairs updated an implementation without updating its full dependent contract:

- Final Java types were still mocked by fixtures that could not mock them.
- Docker source packaging omitted a verifier's transitive Python-runtime helper import.
- Runtime policy and native build changes left generated framework or teaching outputs stale; regenerated education catalog data then invalidated a separately reviewed SAST hash binding.
- New authorization methods were called by production routines without being included in Java source-extraction harnesses. Later partial updates repaired operations coverage while leaving finance harness compilation failures.
- Backend tests introduced an unstubbed actor, attempted to create a second administrator despite the single-admin constraint, and conflated a healthy isolated `FAILED` scenario with provider isolation loss.
- Browser assumptions about request timing and exact accessible labels did not match the actual rendered/request sequence.

These observations support more complete dependency-aware repairs and validation. They do not establish that every failure represented a production security defect. Conversely, fixture failures and canceled jobs cannot establish that production behavior is correct.
