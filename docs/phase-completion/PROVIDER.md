# Separate provider implementation and acceptance

Code implementation is present under [ops/lab-provider](../../ops/lab-provider/README.md). It is independently deployable service source with a restricted offline builder and an actual Firecracker/KVM+jailer launch/inspection/cleanup implementation. It has no emulator/fake production mode. No host, image, provider account, cloud resource, credential, source license, admission signature or production launch has been invented or activated. Application admission remains off by default.

Focused local checks: `python3 -m unittest discover -s ops/lab-provider -p 'test_*.py'` passes **38 tests**; `node --test tests/lab-provider.test.mjs` passes **2 tests**. The latter reruns the Python suite and compares command/result fields directly with `LabProviderClient.java`. Tests include a real Python native HTTP source, revocation, detached-descendant cleanup through a test controller seam, fixed offline compiler selection, isolated imports and stale-socket recovery. No production KVM, systemd cgroup or signed-admission evidence is generated by either command. The execution sandbox does not permit new AF_UNIX listeners; kernel peer credentials and framing are exercised over real connected AF_UNIX socketpairs. Supervisor filesystem/process evidence is simulated separately from the production backend.

Four passes were completed on the owned implementation:

1. Implementation: provider wire protocol, gateway/runner separation, durable state, real supervised microVM lifecycle, guest operation agent and offline build broker.
2. Expert reread: preserved Java record identities; kept root-reviewed inventory independent of application authority; checked no app credentials, arbitrary host upload execution or network devices; matched jailer/vsock/systemd assumptions to primary documentation.
3. Defect hunt: tests exposed and corrected re-recorded command cleanup failures; recovery now includes physical units a restored ledger calls cleaned; socket ownership permits precisely the gateway UID; cgroup inspection uses hierarchical population and actual child membership; linked asset inodes are rehashed; staging time and forced stop are reserved in hard leases; the jailer's PID-file write is allowed by the bounded file-size limit; freeze confirmation protects candidate hashing.
4. Polish: empty/default-deny examples; host/guest service templates; explicit root ownership/mount/UID/bootstrap contracts; isolated Python launch support; precise source/host/fixture distinctions and remaining acceptance below.

The real-provider launch gates remain open. An operator must supply and qualify a separate reviewed host/account, patched hardware/kernel/Firecracker+jailer pair, immutable runtime/build images and exact source/recipe/license mappings, protected HTTPS ingress and credentials, independently held restore epoch and recovery state, real no-egress/tenant/isolation/cleanup/orphan/restore/daemon-death drills, budgets/cost approval, fresh source-bound signed seven-report admission evidence, startup/soak measurements and recruited-user/manual acceptance. The existing `ops/labs/certify.mjs`, V4.8 benchmark checker and application policy remain authoritative; passing this new protocol suite cannot satisfy them.

The supplied guest executor supports fixed reviewed argv handlers over bounded JSON stdin/stdout with guest cgroup cleanup, plus an executable resident HTTP bridge for the six existing native languages. The offline builder supplies fixed Python, Java 17, JavaScript, TypeScript, Go, .NET and PHP recipes. Their real offline toolchains, Redis, data/AI models and IoT runtime mappings still require reviewed image recipes and actual scenario matrices; local source/replay programs are not claimed to have been hosted by this task. These are concrete image/host qualification inputs and do not permit uploads to execute on the application host.
