# Admission, withdrawal, restore and rollback drills

Run drills first in a disposable isolated staging deployment using synthetic accounts, reviewed source and provider TEST payments. CI test fixture results are useful software regressions; they do not attest a real deployment's isolation, backup key custody, object recovery or LIVE merchant readiness. Operators record UTC start/end, deployed revision, provider operator epoch, backup/object/build digests, fixed sanitized control facts and accountable owner handles. Retain detailed traces under restricted access; attach their SHA-256 digest, never a cookie, protected package or payment payload, to release evidence.

## Budget and admission pause

1. Confirm current fresh-MFA administrator access and capture the operations baseline: cumulative admitted/healthy/pending counters, provider epoch, active reservations, daily/monthly reservations and budget limits. Record approved monetary units exactly; the API uses integer micros, not rounded display currency.
2. In disposable staging, place actual reservations at the declared daily/monthly cap using the existing backend test/provider fixture. Submit one additional eligible run through the normal API. It must fail with `LAB_CAPACITY` before a new `lab_runs` reservation or provider command exists. Test racing accounts, global occupancy, memory and separate class quotas as well. Existing `LabsIntegrationTest.reservationAtMonetaryCapBlocksAdmissionAndReportsBudgetPressureWithoutCreatingAuthority` and the quota race tests exercise the software contract on real PostgreSQL; use the immutable final-head CI log as the CI trace.
3. Exercise `POST /api/v1/admin/labs/pause-admissions` with `paused: true` and a reason through the authenticated application and existing CSRF protection. A nonadministrator and stale-MFA session must be denied. The operation must be audited and new reservations blocked. Public catalogue/source access remains coherent; active cleanup continues.
4. Do not delete financial rows, reset counters or refund capacity manually. Uncertain provider cleanup must retain reservation/accounting capacity and show operator attention. Confirm quota/budget pressure is visible and that the configured on-call alert destination actually receives the incident signal. A dashboard condition alone does not certify alert delivery.
5. Resume only after the accountable operator checks current signed admission evidence, capacity, cleanup and provider epoch. Record `BUDGET_STOP` and `ADMISSIONS_PAUSE` facts. `budgetExceeded` must be false.

## Withdrawal and capability revocation

1. Create one reviewed public source version, one entitled synthetic buyer and one nonentitled account. Record package/version hashes and lawful ledger/entitlement counts without putting package bytes or identities into the evidence.
2. Withdraw/suspend the current listing using its existing authenticated moderation/commerce workflow. New discovery/sales and source-linked admission must close. Existing lawful purchases and historical immutable source versions must retain their prescribed access. An already downloaded free archive cannot be recalled; do not claim otherwise.
3. Revoke the current source or account authority for an admitted isolated run. Old request/event routes must close before provider cleanup completes. Queued revoked work must not start. Verify owner-private identifiers remain unavailable to the other account and that protected source URLs fail for unauthorized actors.
4. Confirm cleanup against the actual provider. Do not equate a stop request, an expired UI timer or lost response with confirmed resource deletion. Preserve uncertain reservations and orphan attention until confirmed cleanup; inspect the separate stale-worker/orphan alerts.
5. Existing backend regressions include `currentSourceAndAccountRevocationCloseRunAndNeverLeakOtherRuns`, `currentReviewedReleaseReplacesFirstPublicationAndStableRetryClosesRevokedSource`, the IoT/data-AI revocation cases and commerce entitlement/withdrawal tests. Record `WITHDRAWAL`, `CAPABILITY_REVOCATION`, `CLEANUP` and `FINANCIAL_SOURCE_RETENTION` independently.

## Encrypted restore and old authority rejection

1. Quiesce admissions and paid provider mutations using existing application controls and deployment flags. Preserve read access only where safe. Record a consistent backup timestamp and transaction boundary; reserve a new isolated restore target. Never overwrite the active database during a rehearsal.
2. Authenticate the encrypted archive before sending any bytes to PostgreSQL. A modified AEAD tag must fail before restore. Restore schema/data into a disposable target with the documented migration/runtime role separation. Validate migration history, administrator roles, moderation state, lawful inquiries/reviews, source version/package hashes, purchase entitlements, pending/refund/transfer records and immutable ledgers.
3. `scripts/verify-restore-ci.mjs` is intentionally CI-only: it requires the disposable CI compose project and synthetic administrator. It uses a real PostgreSQL dump/restore with AES-256-GCM, rejects tag corruption and compares relevant row counts and retained business state. Run it through the existing Docker CI workflow. It is not a production backup or key management command and does not by itself prove recovery of all external protected object bytes.
4. In the actual operator drill, also restore private object versions under their intended encryption/permissions and independently verify immutable package hashes through the authorized entitlement path. Test anonymous/foreign-account denial, retained lawful access and complete financial/source consistency. Measure actual backup age (RPO target at most 15 minutes) and elapsed recovery time (RTO target at most 4 hours); CI fixture timing does not establish production RPO/RTO.
5. Rotate the provider's operator epoch and execution secrets outside the restored database before reconnecting a deployment. The application must quarantine old leases, pause admissions and reject old run request/replay/capability routes. **Never restore active execution authority from a database backup.** Restore counters may look identical; the independent provider epoch must differ and old capabilities must remain unusable.
6. Reconcile orphan resources with the isolated provider and record confirmed cleanup. Keep runtime disabled until independently signed admission evidence for the new epoch has passed the existing certification verifier. A restored deployment begins a new soak; it cannot append to the old runtime authority cohort.
7. Record `RESTORE`, `CAPABILITY_REVOCATION`, `CLEANUP` and `FINANCIAL_SOURCE_RETENTION`. A PASS requires actual authenticated archive, matching counts, measured RPO/RTO, denied old capabilities and retained lawful source/financial records.

## Rollback without losing lawfully retained records

1. Pause admissions, stop any independently enabled payment lane according to its existing callback/reconciliation procedure, and retain signed provider webhook verification and settlement/reconciliation access needed for already committed money state. Do not abandon pending captures/refunds or run an automatic destructive downgrade.
2. Pin the last reviewed compatible application build, its source revision, image digest, database schema contract and source package hashes. Confirm the rollback binary understands the deployed migrations. Use forward-compatible schema evolution; if compatibility is unknown, keep the deployment paused and fix forward instead of dropping tables or history.
3. Deploy the known compatible build to a limited signed-in cohort. Check anonymous/private byte boundaries, existing lawful entitlements, source withdrawal, payment idempotency, immutable ledgers and configured-backend failure honesty. Replay signed provider TEST callbacks on staging to verify duplicate/refund/transfer processing preserves authority.
4. Confirm admissions remain paused until the operator reviews configuration, current provider epoch, orphan cleanup and separate live gates. Runtime and merchant readiness are independent; do not turn one on because the other passed.
5. Observe public catalogue/source health, protected package access, money reconciliation and stale-worker/quota/orphan alerts after rollback. Record `ROLLBACK` and `FINANCIAL_SOURCE_RETENTION` with immutable traces. An incident causes a new release decision and, where source/profile/epoch changed, a fresh seven-day evidence sequence.
