# Threat Model

getLancer is a proof-of-work marketplace with discovery, accounts, builder publishing, private team/business workspaces, delivery/source commerce, recurring maintenance, reviewed static previews, and optional isolated learning runtimes. The frontend is React through vinext/Cloudflare Worker; connected requests cross a frontend proxy into a Spring Boot API backed by PostgreSQL, SMTP and private S3-compatible storage. Disconnected preview, explicit local development, and hosted staging/production are materially different modes. Hosted demos, payments, maintenance and hosted labs have independent activation controls. Scope: current archive '.', excluding ancestor Git/history. This is a focused architecture map, not completed security-review coverage. ## Assets

- Account identity, password hashes, expiring session/challenge/token hashes and administrator authority. Ordinary sessions last 24 hours; administrator sessions last one hour. Administrator password verification creates a five-minute MFA challenge rather than a full session; successful TOTP consumes that challenge. - Administrator TOTP ciphertext is encrypted using the externally supplied MFA_KEYRING/MFA_ACTIVE_KEY_ID, with AES-GCM associated data binding user UUID and key version. Local setup stores generated keys in repository-root .env; hosted processes receive injected values. Ciphertext and the independent keyring both matter to recovery. ## Trust Boundaries

- Browser to frontend/API: the proxy checks same-origin mutation Origin and X-Requested-With, forwards only selected headers, encodes route segments, bounds bodies, disables automatic redirects and restricts OAuth redirect destinations. The API separately enforces exact configured Origin/CORS, request-size limits and route-template rate buckets. Evidence: app/api/v1/[...path]/route.ts:20-54; backend/src/main/java/com/getlancer/security/BrowserSecurityFilter.java:29-108.
- Frontend platform to trusted client identity: Cloudflare runtime bindings override process configuration. The proxy sends X-GetLancer-Proxy and uses only cf-connecting-ip for asserted client identity; the API accepts that identity only after constant-time proxy-secret comparison. Generic forwarded headers are disabled. Evidence: lib/server.ts:4-13; app/api/v1/[...path]/route.ts:27-32; backend/src/main/java/com/getlancer/security/Security.java:56-66; backend/src/main/resources/application.properties:116.
- Session to route authority: unknown routes default to denied. SESSION, DEVELOPER and ADMIN_MFA policies are independently enforced. Administrator mutations and specified private exports additionally require MFA within fifteen minutes. CAPABILITY and SIGNED_WEBHOOK classifications permit dispatch but explicitly leave token/signature verification to domain handlers. - Authenticated user to another owner/tenant: route-level authentication does not replace domain scoping. Team actions use membership plus capability-specific role checks; business access checks current active, verified membership and owner role when requested. Inquiry confirmation capabilities bind both inquiry UUID and action kind. ## Attacker Capabilities

- An anonymous Internet caller can submit public HTTP inputs, route/query/header values, public discovery reads and login/signup attempts; they do not initially possess an authenticated session, administrator MFA, service secret, provider signing secret or operator configuration. Relevant dispatch controls: backend/src/main/java/com/getlancer/security/AuthorizationService.java:56-69; backend/src/main/java/com/getlancer/security/BrowserSecurityFilter.java:69-108.
- A normal authenticated account can control its submitted forms, permitted uploads and its own resources. Cross-owner/team/business access would require defeating current domain authorization, rather than merely possessing a session. Evidence: backend/src/main/java/com/getlancer/business/BusinessRepository.java:60-72; backend/src/main/java/com/getlancer/teams/TeamService.java:70-81; backend/src/main/java/com/getlancer/media/MediaService.java:337-345.
- A holder of a matching inquiry capability can perform its specifically bound action; possession does not grant administrator or arbitrary-inquiry authority. A temporary signed upload URL grants its pending-object operation until expiry, not access to a verified media key or the bucket generally. Evidence: backend/src/main/java/com/getlancer/inquiries/InquiryContractService.java:28-44; backend/src/main/java/com/getlancer/media/MediaService.java:238-306.
- A malicious package author controls submitted static/source bytes within application workflows. Published browser scripts and externally linked demo servers are untrusted. Publisher administration, storage credentials and lab operator certification are absent starting privileges. - A public demo server can influence DNS, HTTPS responses and redirects in the optional demo-health check. The checker validates each target and resolved addresses, connects to a selected resolved address with hostname verification, and follows a bounded number of redirects. Evidence: backend/src/main/java/com/getlancer/trust/DemoHealth.java:87-111; backend/src/main/java/com/getlancer/trust/DemoHealth.java:120-176.

Local Compose database-owner credentials and filesystem access are trusted operator authority, not an invented tenant-isolation boundary. ## Security Objectives

- User-requested objective: secure every API and preserve administrator, owner, tenant and capability boundaries. Route policy, domain authorization and service/signature controls must be evaluated separately, including revocation and stale authority.
- User-requested objective: keep keys/environment secrets out of browser bundles, public files, logs and reports; maintain password/token secrecy and safe administrative bootstrap/recovery. Material consumers include local .env, hosted injected configuration, encrypted MFA state, transient email bodies and external provider requests.
- User-requested objective: enforce validation, XSS/CSP, CORS/CSRF, security headers, debug/error suppression and safe redirect/request destinations. Implemented framework controls include strict JSON coercion/unknown-field rejection and generic API error settings. Evidence: backend/src/main/java/com/getlancer/config/SecurityConfiguration.java:54-69; backend/src/main/resources/application.properties:16-21.
- Preserve immutable package/publication identity through review, reservation, application, reply verification and later gateway readback; distinguish publisher secret authority from current Java eligibility. Evidence: backend/src/main/java/com/getlancer/hosting/HostingService.java:54-63; backend/src/main/java/com/getlancer/hosting/DemoPublisherClient.java:39-61; ops/demo-publisher/server.mjs:459-474.
- Preserve signed financial-event identity and exact provider destination while preventing arbitrary browser assertions from granting paid rights. Collection activation requires policy/provider approvals and credentials; maintenance adds its independent approval/secret controls. Source defaults include 10 DB connections, mutation/auth/email/discovery limits of 30/10/3/300 per minute, 64 KiB webhook/lab requests, and a four-request Razorpay semaphore. These are controls to assess, not capacity certification.
